# SupplySentry Public Demo and Portfolio Release Design

**Date:** 2026-09-13  
**Status:** Approved design  
**License:** AGPL-3.0-only, with alternative commercial licensing available by separate agreement

## 1. Purpose

Turn the public SupplySentry repository into a verifiable portfolio release rather than a source dump. A reviewer must be able to understand the product quickly, run it without private infrastructure, interact with a safe online environment, inspect measured evaluation results, and follow the system boundaries from a single architecture diagram.

This release adds five coordinated deliverables:

1. A writable but isolated public full-stack demo.
2. A one-command Docker startup path backed by a public container image.
3. A versioned supplier-reply evaluation dataset and reproducible reports.
4. A short README GIF and a complete walkthrough video.
5. Editable and rendered architecture diagrams integrated into the README.

## 2. Success criteria

- The public demo is available at `http://47.102.116.148:3002` and never reads or writes the existing port-3001 database, credentials, messaging sessions, or connector state.
- A visitor can enter the demo without receiving or entering a private credential.
- A visitor can change synthetic procurement data and observe real API, persistence, approval, Inbox/Outbox, and projection behavior.
- Email, WeChat, WeCom, WhatsApp, ERP, webhook, MCP, and arbitrary file egress are impossible in public-demo mode.
- Demo state is restored atomically at least once per hour and can also be restored by an authenticated internal reset worker.
- A user with Docker can start the prebuilt demo with one repository command. With the image cached, the application becomes healthy within five minutes; a first pull is documented as network-dependent.
- Evaluation metrics are generated by checked-in code from a versioned, checksummed dataset. No metric is manually invented.
- Public evaluation material contains no customer correspondence, real supplier contacts, purchase prices, credentials, or production identifiers.
- The README displays a compact GIF, online-demo link, one-command startup, evaluation summary, and architecture diagram above the long engineering detail.
- The walkthrough video and report identify simulated data and disabled external effects clearly.

## 3. Selected approach

Use an isolated real full-stack demo with synthetic data and deterministic external simulations.

Rejected alternatives:

- A static frontend is safer but cannot demonstrate API contracts, persistence, state transitions, approvals, or recovery.
- A production mirror connected to live DeepSeek, Hermes, email, and ERP would create avoidable disclosure, cost, abuse, and external-side-effect risks.

The selected approach keeps application behavior real up to the external boundary. At that boundary, the demo records an explicitly simulated receipt rather than contacting another system. Simulated receipts must be distinguishable from production receipts in storage, API responses, audit history, and UI labels.

## 5. Public-demo boundary

### 5.1 Dedicated mode

`READYWORK_PUBLIC_DEMO=1` is a separate runtime mode, not an alias for development demo authentication. Production deployment must continue to reject ordinary demo-auth shortcuts. Public-demo mode is accepted only by the dedicated demo Compose topology and applies these invariants:

- Tenant is fixed to `t:public-demo`.
- A dedicated “Enter public demo” action creates a session for a limited demo procurement-manager identity.
- Connector configuration, credential management, tenant administration, raw database export, arbitrary webhook registration, and developer control surfaces are denied.
- Uploads are disabled. Seeded safe attachments remain viewable.
- Every external action is intercepted before connector resolution and written as a `simulated_demo` receipt.
- UI shows a persistent “Public demo · synthetic data · external delivery disabled” banner in both languages.
- API responses expose `demoMode: true` so the client does not infer mode from the URL.

Public-demo mode must fail closed if the dedicated tenant, seed version, or simulation policy is absent. It must never be enabled by query parameter, cookie mutation, or a client-supplied header.

### 5.2 Synthetic scenario

Seed one coherent manufacturing procurement story with stable IDs and timestamps relative to the reset time:

- One normal local PO.
- One supplier awaiting confirmation.
- One vague supplier reply that becomes reviewable AI evidence.
- One partial-shipment PO with remaining quantity still open.
- One delayed import PO with document and transport risk.
- One short-delivery approval awaiting a human decision.
- One accepted simulated Outbox receipt and one uncertain simulated receipt requiring reconciliation.
- Supplier, SLA, route, notification, message-draft, and audit records connected to those orders.

Every name, email domain, item code, price, attachment, and identifier is fictional. Email addresses use reserved domains such as `example.com` or `example.test`.

### 5.3 Reset protocol

The control API owns an internal `POST /internal/demo/reset` route that exists only when `READYWORK_PUBLIC_DEMO=1`.

- Request authentication uses the existing internal-token boundary.
- The reset acquires a database lease so only one reset runs at a time.
- All deletion and reseeding are scoped to `t:public-demo` and committed in one SQLite transaction.
- The operation increments a visible demo generation and appends a reset audit event.
- A dedicated reset service calls the route at startup and every hour.
- Concurrent user mutations either complete before the reset transaction or receive a stable reset/version-conflict response and refresh.
- Failure leaves the previous generation intact and marks demo health degraded; it does not partially seed data.

The existing production database path and `/opt/readywork/shared/data` volume are never mounted into the demo topology. Demo state uses a dedicated named volume.

## 6. Docker and container publishing

### 6.1 One-command experience

The documented command is:

```bash
./scripts/demo/demo.sh up
```

The script:

1. Checks Docker and Compose availability.
2. Creates an ignored local environment file with cryptographically random internal and session secrets when absent.
3. Pulls `ghcr.io/het2333/supply-sentry-demo:latest` by default.
4. Starts the demo topology and waits on explicit health checks.
5. Prints the local URL and the exact command for logs and shutdown.

`./scripts/demo/demo.sh down` stops containers without deleting the named volume. `./scripts/demo/demo.sh reset` invokes the internal reset route. `./scripts/demo/demo.sh purge` is the only command that removes demo state and must require an interactive confirmation.

### 6.2 Topology

The demo Compose stack contains:

- Console.
- Business API.
- Control API.
- Temporal database and Temporal service.
- Temporal worker using the deterministic mock-model path.
- Mock model.
- Reset worker.

Hermes, email, ERP, and production DeepSeek credentials are absent. Only the console port is published; all other services remain on the private Compose network. Local startup binds to `127.0.0.1` by default. Server deployment explicitly overrides the console binding to `0.0.0.0:3002`.

### 6.3 GHCR workflow

The image workflow builds on `main` and version tags, pins Node and pnpm, uses GitHub’s short-lived package token, emits an OCI source label, and publishes immutable commit-SHA and version tags. `latest` advances only after tests, seed verification, and container health checks pass.

No runtime secret is built into an image layer or image metadata.

## 7. Evaluation design

### 7.1 Dataset truthfulness

The dataset contains 240 representative, labeled supplier-reply cases derived from procurement communication patterns, not copied customer messages. It is explicitly labeled `synthetic_contract_case`. “Real evaluation” means the published numbers are produced by actually executing the parser/model against these records; it does not mean the records are represented as real customer data.

The dataset covers:

- Chinese, English, mixed-language, and QQ-style formatting.
- Exact dates, relative dates, vague dates, conflicting dates, and missing years.
- Full quantity, partial quantity, unannounced split delivery, and quantity shortfall.
- Price and currency changes.
- Production, shipment, ASN, carrier, tracking, ETA, and receipt claims.
- Quoted history and forwarded-message contamination.
- Wrong supplier, wrong PO, multiple candidate POs, and absent identifiers.
- Missing facts, contradictory facts, low confidence, and required human review.

### 7.2 Record contract

Each JSONL row contains:

- Stable case ID, dataset version, locale, scenario tags, and provenance.
- Received timestamp and sanitized message body.
- Candidate supplier and PO context.
- Expected PO association.
- Expected extracted fields with exact evidence spans.
- Expected unknown fields.
- Expected validation result and approval requirement.
- Difficulty and adversarial flags.

The JSON Schema rejects unknown fields. A dataset verifier checks unique IDs, evidence spans, reserved contact domains, forbidden secret patterns, date validity, label consistency, class balance, and a committed SHA-256 digest.

### 7.3 Runners and reports

Provide two runners behind the same contract:

- `deterministic`: runs in CI without credentials and protects parser and validation regressions.
- `deepseek`: opt-in, reads a provider key only from the process environment, uses the production structured-output path, and never writes the key or raw provider response to reports.

Reports record dataset hash, Git commit, runner, model, prompt/schema version, time, token counts, latency distribution, and pricing snapshot. Metrics include:

- PO association accuracy.
- Field precision, recall, and F1 for delivery date, quantity, price, production, and shipment.
- Missing-fact recall.
- Short-delivery and material-variance approval recall.
- Fabrication rate.
- End-to-end accepted-result rate.
- P50/P95 latency and token cost when available.

CI regenerates the deterministic report and fails if it differs from the committed expected summary. A DeepSeek report is published only after a real successful run; missing provider access is reported as unavailable, never replaced with an estimate.

## 8. Demo GIF and walkthrough video

The capture script uses a fixed 1440×900 viewport, the seeded demo generation, and a deterministic clock. It records only the demo tenant.

### 8.1 README GIF

Target duration is 15–20 seconds and target size is below 8 MB. The sequence is:

1. Enter public demo.
2. Open the risk order.
3. Review the supplier reply and extracted evidence.
4. Approve the pending short-delivery decision.
5. Show the order projection, notification, and audit update.

The GIF has no audio, uses readable pauses rather than rapid cursor motion, and includes a visible demo/simulation banner.

### 8.2 MP4 walkthrough

Target duration is 60–90 seconds, 1080p H.264, with concise bilingual-safe on-screen captions. It covers the same primary story plus supplier directory, SLA, Inbox/Outbox, and architecture summary. It contains no production URLs, user accounts, browser bookmarks, desktop notifications, credentials, or real contacts.

The MP4 is uploaded to a versioned GitHub Release. The poster and GIF remain in the repository so the README never depends on an unauthenticated video embed.

## 9. Architecture diagram

The editable Draw.io source is authoritative; the SVG is a generated presentation artifact. The diagram uses three visually explicit boundaries:

1. Human and channel inputs.
2. SupplySentry trusted business runtime.
3. External systems and side effects.

The main flow is:

```text
Console / Inbox
  → Business and Control APIs
  → Temporal workflow
  → Manufacturing Context snapshot
  → DeepSeek structured proposal
  → Schema and evidence validation
  → Human approval when required
  → Action Gateway
  → Inbox/Outbox
  → Hermes, Email, ERP, or Warehouse
  → external receipt
  → SQLite facts, projection, SLA, risk, and audit
```

The diagram labels the safety rule “Model proposes; business runtime decides” and distinguishes decision data from side-effect commands. Colors must remain legible in light and dark GitHub themes, text must remain selectable in SVG, and the rendered diagram must fit the README width without horizontal scrolling.

## 11. CI and verification

Add a GitHub Actions workflow using Node 24 and pnpm 11.7.0. Pull requests and `main` run:

1. Frozen dependency installation.
2. Type check.
3. Existing test suite.
4. Localization tests.
5. Deployment-contract tests.
6. Deterministic supplier-reply evaluation and report-diff check.
7. Demo seed verifier.
8. Demo Compose render check.
9. Console production build.
10. Container build and health smoke test where runner capacity permits.

Media capture and remote DeepSeek evaluation are manual workflows because they are slow or credentialed. The GHCR publish job runs only after mandatory checks pass.

## 12. Server deployment

Deploy the demo under a separate server directory and Compose project name, for example `/opt/supplysentry-demo` and `supplysentry-demo`. It uses dedicated Docker volumes, generated secrets, and port 3002. It does not mount or copy `/opt/readywork/shared`, the production deployment environment, production SQLite files, Hermes state, or DeepSeek credentials.

Before opening port 3002, verify locally on the server:

- All containers are healthy.
- Demo mode and seed version are visible.
- Connector and credential endpoints are denied.
- A simulated approval changes only the demo tenant.
- Reset restores the initial generation.
- Container environment and logs contain no production secret or customer data.

After those checks, allow inbound TCP 3002 in the host and Alibaba Cloud security group. The public URL is added to the README only after an external browser verifies it.

## 13. Error handling and abuse controls

- Rate-limit login, mutations, search, chat, and reset-sensitive reads per IP and demo session.
- Cap request bodies and disable public uploads.
- Reject non-demo tenant identifiers at the API boundary.
- Never accept external connector credentials in public-demo mode.
- Treat simulated post-dispatch uncertainty as a visible reconciliation state rather than a success.
- Show stable bilingual errors for reset conflicts, rate limits, and temporarily unhealthy demo state.
- Do not log message bodies, tokens, cookies, or provider payloads.
- Apply noindex metadata to the live demo while allowing the GitHub repository to remain discoverable.

## 15. Acceptance evidence

Completion requires all of the following evidence:

- Clean secret scan of current files and Git history.
- Full repository tests, type check, console build, and deployment contracts passing on Node 24.
- Demo boundary tests proving external connectors cannot be invoked.
- Docker startup and health output from a clean environment.
- Evaluation dataset validation and report reproduction with exact case counts.
- Visual inspection of architecture SVG, GIF, poster, and README at desktop and narrow GitHub widths.
- External browser verification of the online demo and public GitHub links.
- Server evidence showing port/volume/process isolation from the existing deployment.
- GitHub Release evidence for the MP4 and GHCR image tags.

No completion claim may substitute an existing production deployment, a static mock, an estimated evaluation score, or a README statement for these checks.
